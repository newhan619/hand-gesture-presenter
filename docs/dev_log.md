## 2026-11-11 제안서 작성

**진행 내용:** 사용자 요청과 수업 안내, 샘플의 구성을 바탕으로 제안서와 요구사항을 한 Word 파일로 작성했다. 핵심 기능 3개와 선택 기능을 구분하고 초기 제스처 규칙과 검증 목표를 정했다.

**사전 확인:** MediaPipe 공식 설치 문서는 Python 3.9~3.14를 지원 범위로 안내한다. Python 3.11 64비트를 개발 후보로 정했으며, 실제 가상환경과 패키지 설치는 사용자 확인 후 진행한다. 최신 Tasks API의 Hand Landmarker를 우선 검토한다. OpenCV는 GUI 배포판 하나만 사용한다.

**AI 초안:** 이번 단계에서는 프로그램 코드를 생성하거나 실행하지 않았다. 제안서의 프레임 수, 이동 거리, 쿨다운 및 스무딩 수치는 시험할 초기값이며 검증된 결과가 아니다.

**요구사항을 구체화한 내용:** 반전된 미리보기 기준 오른쪽 스와이프를 다음 장으로 정의했다. 포인터와 스와이프를 동시에 실행하지 않도록 모드를 나누고, 손 미검출 시 좌표 이력을 초기화하는 계획을 넣었다. 이는 예상 충돌을 줄이기 위한 설계이며 실제 버그 수정 사례가 아니다.

**남은 확인:** 개발 Python의 로컬 설치 여부, MediaPipe와 OpenCV 의존성, 웹캠 사용, PowerPoint Ctrl+L 및 Ctrl+A 동작과 창 포커스, 발표 PC의 처리 속도.

## 2026-11-15 최종 제안서 기반 로컬 초기 구현

**구현 목표:** 최종본의 세 가지 핵심 기능에 맞춰 손 인식·관절 표시, 스와이프와 검지 포인터, 유지 프레임·쿨다운·스무딩을 구현했다. 사용자 제스처 학습과 판서는 구현하지 않았다. Word 제안서는 수정하지 않았다.

**실행 환경:** 일반 설치 Python과 `py` 런처는 확인되지 않았으나 Codex가 제공하는 Python 3.12.14 64비트를 사용할 수 있어 프로젝트 `.venv`를 만들었다. MediaPipe 1.2.3, opencv-contrib-python 4.14.0.94, NumPy 2.5.4, PyAutoGUI 0.9.54를 설치했다. MediaPipe의 의존성에 맞춰 GUI OpenCV는 contrib 배포판 하나만 사용했다. 전체 설치 버전은 `requirements.lock.txt`에 기록했다.

**AI 초안과 원리:** 카메라 처리와 제스처 계산을 분리했다. `core.py`는 관절 각도·상대 거리로 손가락을 판별하고, 시간과 좌표를 받아 이벤트만 만든다. 실제 입력은 `output.py`에 모았다. 모양을 5프레임 유지한 뒤 인정하고, 편 손의 손바닥 중심이 0.5초 내 너비 20% 이상 이동하면 방향을 판단한다. 한 번 넘긴 뒤에는 주먹 복귀와 1초 경과를 모두 요구한다. 포인터 모드에서는 슬라이드 이벤트가 발생하지 않는다.

**실제 발견한 문제와 수정:**

- 느린 이동 테스트에서 준비 위치를 x=0.4로 둔 뒤 첫 이동 좌표를 x=0.2로 넣어, 테스트 자체가 빠른 왼쪽 스와이프를 만들었다. 준비 위치를 x=0.2로 맞춰 연속적인 느린 이동으로 수정했다. 이 문제는 제스처 알고리즘의 결함이나 실제 웹캠 실패로 기록하지 않는다.
- `run.ps1 -Mode demo` 실행 시 인자가 `- - d e m o`로 전달되어 argparse가 종료 코드 2를 반환했다. PowerShell `switch` 결과가 값 하나일 때 문자열이 되고, 이를 splat하면서 글자로 분리된 것이 원인이다. `@(switch ...)`로 결과를 항상 배열로 만들었다. 수정 후 같은 명령을 다시 실행해 PASS를 확인했다.

### 손가락 판별에 world 좌표 대신 화면 좌표 사용 (2026-11-16)

- 구현 목표와 관련 요구사항: 0~5개 손가락과 주먹·편 손·검지 판별(구현 계획 3단계).
- AI가 처음 제안한 코드와 원리: `classify_hand`가 MediaPipe world 좌표(한 장의 영상에서 추정한 미터 단위 3D 좌표)로 관절 각도를 계산하고, 손가락 가운데 마디 155°·끝마디 150° 이상이면 펴짐으로 판정했다. 손을 돌려도 각도가 유지된다는 이유로 world를 우선했다.
- 실제 발생한 문제와 재현 조건: macOS, MacBook 카메라(1번), 왼손, 손바닥이 카메라를 향한 상태에서 1개(검지)를 제외한 2~5개가 틀렸다. 사용자 관찰은 "2개→0 FIST, 4개→1 OTHER, 5개→2 OTHER, 숫자가 자주 바뀜". 진단 스크립트(저장소 외부)로 라벨별 좌표를 기록했다. world 좌표에서는 편 손의 검지 끝마디가 약 142°, 중지 가운데 마디가 약 144°로 계산돼 기준을 넘지 못했다. 같은 프레임의 화면 좌표 각도는 대부분 170° 이상이었다.
- 팀이 직접 수정한 코드와 이유: `camera.py`에서 `classify_hand`에 world를 넘기지 않고 가로세로 비율을 보정한 화면 좌표만 쓰게 했다. 기준값은 바꾸지 않았다. `core.py`의 world 지원과 재생 기능은 그대로 두었다. 재현 테스트 `test_shape_uses_image_landmarks_not_curled_world_estimate`를 추가했다(화면 좌표는 편 손, world는 주먹인 가짜 프레임).
- 수정 전 실행 결과: 새 테스트가 `Left | FIST | fingers: 0`으로 실패. 기록한 왼손 717프레임을 기존 경로로 다시 판정하면 0개 81/81, 1개 70/70, 2개 0/59, 3개 0/291, 4개 0/110, 5개 0/106 정답.
- 수정 후 실행 결과 및 확인 환경: macOS, Python 3.12.16에서 자동 테스트 35개 통과, `--demo` PASS. 같은 기록 717프레임을 수정 경로로 다시 판정하면 0~5개 모두 100% 정답(2개·3개·4개는 OTHER, 5개는 OPEN). **기록 좌표의 재계산 결과이며 실시간 웹캠 확인은 아직 하지 않았다.** 오른손 기록은 없다.
- 핵심 원리 설명: world 좌표는 평면 영상에서 깊이를 추측한 값이라 손가락이 실제보다 굽은 것처럼 나올 수 있다. 화면 좌표는 영상에 찍힌 위치 그대로라 손바닥이 카메라를 향할 때 손가락이 곧게 펴진 모양이 각도에 그대로 드러난다. 가로세로 비율을 곱하는 이유는 정규화 좌표의 가로 1과 세로 1이 실제 픽셀 길이가 달라서 각도가 찌그러지기 때문이다.
- 배운 점과 남은 한계: 합성 좌표 테스트는 world 추정 오차를 만들지 않아 이 문제를 찾지 못했다. 화면 좌표는 손가락이 카메라 쪽으로 기울면 길이가 짧아 보여 판정이 틀릴 수 있다. 오른손, 손 기울기, 조명·거리 조건은 미확인이다.
- 사용자 확인 및 다음 단계: 사용자가 수정 후 preview(macOS, 카메라 1번)에서 왼손·오른손 0~5개를 확인했다. "이전보다 정확도가 훨씬 늘었다"고 보고했다. 손바닥 정면, 손등, 손날을 보여 준 경우 모두 정상이었다. 손가락이 카메라를 향한 경우에만 숫자가 깜빡이며 잘 판별하지 못했다. 단일 카메라 2D 좌표의 한계로 보고 수정하지 않는다. 체크리스트 기준의 손 모양별 5회 성공/실패 횟수는 기록하지 않았다. 다음은 5프레임 유지 조건과 손 미검출·두 손 정지를 확인한다.

## 2026-11-27 데스크톱 모드 macOS preview 시험

**환경:** macOS, MacBook 카메라 1번, FPS 약 30, `bash run.sh desktop-preview 1`(모의 입력).

**사용자 관찰:** 편 손을 좌우로 빠르게 움직이면 순간적으로 손가락 4개로 인식되고 `Action`이 `IDLE`로 바뀌어 창 전환이 안 됐다. 엄지·검지를 붙이고 움직이는 도중 `drag_end`가 나오고 바로 다시 `drag_start`가 됐다.

### 창 전환: 짧게 끼는 OPEN이 아닌 프레임은 이동 기록 유지 (2026-11-27)

- 구현 목표와 관련 요구사항: 편 손 좌우 스와이프로 창을 한 번 전환한다(체크리스트 데스크톱 모드).
- AI가 처음 제안한 코드와 원리: `DesktopController.update`가 OPEN이 아닌 프레임이 하나라도 오면 `swipe_history`(손바닥 위치 기록)를 지웠다. 전환은 이 기록에서 0.5초 안에 화면 너비의 19% 이상 이동했는지로 판단한다.
- 실제 발생한 문제와 재현 조건: 빠르게 움직이면 영상이 번져 한 프레임이 손가락 4개(OTHER)로 판정된다. 그 순간 기록이 지워져 이미 움직인 거리가 사라지고 전환에 필요한 거리를 다시 채우지 못했다. 사용자가 원인으로 추측한 위치(`desktop.py`의 OPEN이 아니면 기록 삭제)를 코드에서 확인했다.
- 팀이 직접 수정한 코드와 이유: 사용자가 원인과 수정 방향을 제시했고, 그에 따라 Claude Code가 수정 코드를 작성했다. OPEN이 아닌 상태가 시작된 시각(`swipe_gap_since`)을 기억해 `DesktopConfig.swipe_grace`(0.15초) 이하이면 기록을 유지하고 넘으면 지운다. 끊긴 프레임의 위치는 기록에 넣지 않는다. 기존 테스트와 맞추기 위해 `swipe_used`(한 번 전환함 표시)는 기존처럼 바로 초기화한다. 손 미검출·주먹 일시정지·핀치가 기록을 지우는 동작은 그대로다.
- 수정 전 실행 결과: 새 테스트 `test_brief_non_open_frame_during_swipe_keeps_history`(OPEN x=0.30, 0.36 → 4개 손가락 한 프레임 → OPEN x=0.50)가 전환 없음으로 실패했다.
- 수정 후 실행 결과 및 확인 환경: macOS, Python 3.12에서 자동 테스트 51개 통과(새 테스트 2개 포함, 0.15초보다 긴 끊김은 기록을 지우는지 확인), `bash run.sh desktop-demo`와 `bash run.sh demo` PASS. 수정 후 사용자가 같은 환경의 웹캠(desktop-preview)에서 편 손 스와이프를 시험해 오른쪽 10/10, 왼쪽 10/10 전환을 확인했다. 잘못된 전환은 없었다.
- 핵심 원리 설명: 스와이프는 여러 프레임에 걸친 이동 거리로 판단하므로 중간의 한 프레임 오판이 전체를 무효로 만들면 안 된다. 짧은 끊김은 흔들림으로 보고, 일정 시간 이상 이어질 때만 손 모양이 실제로 바뀐 것으로 본다.
- 배운 점과 남은 한계: 끊김 허용 시간이 길수록 다른 손 모양을 거쳐 이동한 경우도 스와이프로 인정될 수 있다. 0.15초는 FPS 30에서 약 4프레임이며 실제 시험으로 조정해야 한다.
- 사용자 확인 및 다음 단계: 사용자 웹캠 확인 완료(좌우 각 10/10, 오전환 0회, 모의 입력). 실제 `⌘+Tab` 전환은 desktop 모드에서 따로 확인한다. 다음은 드래그 끊김을 수정한다.

### 드래그: 이미 집고 있으면 손끝 거리만 확인 (2026-11-27)

- 구현 목표와 관련 요구사항: 엄지·검지를 붙인 채 움직이는 동안 드래그를 유지하고, 손가락을 떼면 놓는다(체크리스트 데스크톱 모드).
- AI가 처음 제안한 코드와 원리: 매 프레임 `pinched = 거리 조건 and (검지가 앞으로 뻗음 or 검지 펴짐)`으로 판정했다. 거리는 잡을 때 `pinch_close`(0.24), 집는 중에는 `pinch_open`(0.36) 기준을 썼다. 검지 조건은 주먹에서 손끝이 우연히 가까워진 것을 클릭으로 보지 않기 위한 것이다.
- 실제 발생한 문제와 재현 조건: 집은 채 움직이는 도중 `drag_end`가 나오고 바로 다시 `drag_start`가 됐다. 이미 집는 중에도 검지 조건을 다시 확인해서, 검지가 굽으면 거리가 가까워도 핀치가 풀렸다. 사용자가 추측한 원인을 코드에서 확인했다. 놓은 뒤 바로 다시 잡히는 것은 `_finish_pinch`가 `pinch_ready`를 초기화하지 않아, 손가락이 붙은 채 다음 프레임에 새 핀치가 시작되기 때문이다.
- 팀이 직접 수정한 코드와 이유: 사용자가 원인과 수정 방향을 제시했고, 그에 따라 Claude Code가 수정 코드를 작성했다. 이미 집는 중이면 `pinch_gap < pinch_open`만 보고, 새 핀치를 시작할 때만 기존처럼 검지 조건까지 확인한다. 주먹 일시정지가 먼저 처리되는 순서, 클릭 판정, 손 미검출 시 드래그 해제는 바꾸지 않았다. 손가락이 짧게 벌어지는 것을 무시하는 방법(0.1초)은 놓기와 클릭이 늦어져 기존 테스트·데모의 기대 시간과 충돌한다. 이번 수정으로 부족할 때만 진행하기로 했다.
- 수정 전 실행 결과: 새 테스트 `test_drag_continues_when_index_bends_while_pinched`(드래그 중 손끝은 붙어 있고 검지만 굽은 프레임)가 `drag_move` 대신 `drag_end`로 실패했다.
- 수정 후 실행 결과 및 확인 환경: macOS, Python 3.12에서 자동 테스트 53개 통과(새로 집을 때는 여전히 검지 조건이 필요하다는 테스트 포함), `bash run.sh desktop-demo`와 `bash run.sh demo` PASS. 수정 후 사용자가 같은 환경의 웹캠(desktop-preview)에서 확인했다. 집은 채 움직이는 동안 끊김 없이 드래그가 유지됐고, 손가락을 떼면 `drag_end`가 1번 나왔다. 짧은 핀치 `click`, 드래그 중 주먹·손 빼기 시 `drag_end`도 정상이었다.
- 핵심 원리 설명: 시작 조건과 유지 조건을 나눴다. 잘못된 클릭을 막는 엄격한 조건은 시작할 때만 필요하다. 이미 집은 상태에서는 사용자가 실제로 손가락을 뗐는지, 즉 두 손끝의 거리만 보면 된다.
- 배운 점과 남은 한계: 거리가 한 프레임만 `pinch_open`을 넘어도 놓이는 것은 그대로다. 집는 동안 손 전체가 주먹(검지도 접힘, 앞으로 뻗지 않음)으로 판정되면 일시정지 안전장치가 먼저 동작해 놓인다.
- 사용자 확인 및 다음 단계: 사용자 웹캠 확인 완료(모의 입력, 시도 횟수는 기록하지 않음). 끊김이 재현되지 않아 짧은 벌어짐 무시(2-나)는 진행하지 않는다. 실제 마우스 드래그는 desktop 모드에서 따로 확인한다.

### 수정 후 데스크톱 실제 입력 시험 (2026-11-27)

### 팀원 수정 통합과 스와이프 경계 보완 (2026-11-27)

- 팀원의 macOS 실제 입력 기록, 드래그 유지 조건 수정, 관련 테스트를 통합했다. 드래그 중 주먹 일시정지와 손 미검출 해제는 우선 처리한다.
